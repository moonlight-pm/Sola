# Sola Browser Port — Design

## Context

`apps/browser/` is a working `sola-browser` crate sitting outside the cargo
workspace. Since it was last touched (commits `cbe00f4`, `34f8e72`), the bus
protocol and persistence model have moved on:

- `BusHandler` signatures now take a `Delivery` wrapper (`{topic, retracted}`)
  rather than a bare `&Topic`. The browser's handlers predate this and won't
  compile against current `sola-bus`.
- Persistent topics replaced the `JsonConfig` pattern as the canonical place
  for app state. `sola-terminal` already migrated (`f958b15`, `7425cf4`):
  per-tab `#[persistent(keys = [id])] TerminalSession`, singleton
  `TerminalConfig`. The browser is the only remaining `JsonConfig` user.

Porting verbatim isn't an option (the build breaks); fully aligning with the
current model is. This spec covers both: the relocation, the drift fixes, and
the persistence redesign — plus two small, generic `sola-bus` enhancements that
the new persistence shape requires.

## Goals

- Move `apps/browser/` → `crates/sola-browser/`, joining the cargo workspace.
- Make the browser compile and run against current `sola-bus` / `sola-app`.
- Replace `JsonConfig`-backed JSON files with persistent bus topics that
  mirror the terminal's pattern.
- Add an opt-in `namespace` attribute to persistent topics so the browser's
  state lives in dedicated files instead of inflating the shared `state.toml`.
- Add `Delivery::source` so apps can filter their own self-echoes.

## Non-goals

- Bookmarks, per-site preferences, multi-window browser, download history.
- Extracting history into a `sola-history` sidecar service. (Schema chosen so
  this can happen later without breaking changes.)
- Migrating `TerminalSession` to a `namespace` (separate PR; the namespace
  attribute is opt-in and terminal can adopt it on its own schedule).
- Behavior changes to the browser UI. The web frontend is unchanged. Only the
  Rust state plumbing moves.

## Mechanical relocation

1. `git mv apps/browser crates/sola-browser`.
2. `crates/sola-browser/Cargo.toml` — update three path dependencies:
   `../../crates/sola-app` → `../sola-app` (and same for `sola-bus`,
   `sola-core`).
3. Delete `apps/browser/Cargo.lock` (the workspace lockfile takes over).
4. Workspace `Cargo.toml` is `members = ["crates/*"]` — no change needed.
5. `CLAUDE.md`: remove the `browser/             # WebKit browser (not in
   workspace yet)` line from the `apps/` listing; add `sola-browser/` to the
   `crates/` listing.

`include_str!("../web/...")` paths in `main.rs` are relative to the source
file and survive the move untouched. `sola-make`'s `discover_binaries`
already scans `crates/*` and will pick up `sola-browser` automatically;
`cargo make install browser` resolves via the existing
`resolve_crate_name` fallback (`crates/browser/Cargo.toml` not found →
falls back to `sola-<name>` → `sola-browser`).

## sola-bus enhancement 1: `namespace` attribute

### Grammar

```rust
#[persistent(namespace = "browser")]                          // singleton → browser.toml
BrowserConfig(BrowserConfig),

#[persistent(namespace = "browser/history")]                  // singleton → browser/history.toml
BrowserHistory(BrowserHistory),

#[persistent(keys = [id], namespace = "browser/tabs/:id")]    // per-key files
BrowserTab(BrowserTab),
```

The attribute is **optional**; topics without it keep landing in the shared
`~/.config/sola/state.toml` exactly as today. Backward-compatible.

`:name` placeholders interpolate from the `keys = [...]` array by name. The
macro validates at compile time that every `:name` matches an entry in the
keys list. Multi-key interpolation is supported by construction
(`namespace = "windows/:app_id/:window_id"`), even though no current topic
uses more than one key — keeping the grammar key-arity-agnostic now means
nothing has to change later.

### Slugification rules

Each interpolated key value must satisfy:

- non-empty
- no `/`, no `\0`, no `..` segment

Violations are rejected at emit time with a clear error log; the topic is not
stored. UUIDs and `app_id`-style identifiers (the only key shapes in use
today) all pass trivially. If a future topic ever wants `keys = [url]`, it
should hash or percent-encode the URL itself before passing it as a key —
the bus stays out of policy.

### Path resolution

```
namespace = "browser"               → ~/.config/sola/browser.toml
namespace = "browser/history"       → ~/.config/sola/browser/history.toml
namespace = "browser/tabs/:id"      → ~/.config/sola/browser/tabs/<id>.toml
(no namespace, persistent topic)    → ~/.config/sola/state.toml
```

A `Topic::path_for(&self) -> Option<PathBuf>` method generated by
`define_topics!` returns the resolved path (or `None` for non-persistent
topics).

### Storage routing in `state.rs`

The existing parse → replace section → atomic temp+rename logic generalizes:
operate on the topic's resolved path instead of the hardcoded `state.toml`.
Per-key-file topics simplify retract — it's `unlink(path)` instead of
parse+drop-section+rewrite.

### Loading at bus startup

For each persistent topic kind, the bus enumerates files matching its
namespace pattern:

- Plain string (e.g., `"browser"`): read one file if it exists.
- With `:key` interpolation: walk the parent directory, treat each file
  whose name matches the pattern as one keyed sticky message; recover the key
  values from the path.

Each loaded file becomes a sticky `Message` tagged
`source = "sola-bus"` (`BUS_SOURCE`) — same as today's `state.toml` replay.

### Atomicity caveat

Today, a single emit = one atomic file write covering all persistent topics.
With `namespace`, related topics may live in different files; a crash mid-
update can leave inter-topic references dangling (e.g., `BrowserConfig.active_tab_id`
referencing a `BrowserTab` whose file hasn't been written yet). The browser
handles this at the application layer (see *realize_active*); no
cross-file transactionality is added to the bus.

## sola-bus enhancement 2: `Delivery::source`

`Delivery` currently exposes `topic` and `retracted` only:

```rust
// crates/sola-bus/src/registry.rs:10
pub struct Delivery<'a> {
    pub topic: &'a Topic,
    pub retracted: bool,
}
```

The underlying `Message::source` already exists and is set on every
`BusClient::send`. The dispatch construction site
(`crates/sola-app/src/lib.rs:367`) just doesn't propagate it. Extension:

```rust
pub struct Delivery<'a> {
    pub topic: &'a Topic,
    pub retracted: bool,
    pub source: &'a str,    // app_id of emitter, or "sola-bus" for restored stickies
}
```

Source values seen in handlers after this change:

- `"sola-browser"` (or any app_id) — live emit by that app.
- `"sola-bus"` — sticky restoration on startup (the `BUS_SOURCE` constant).

Existing handlers that don't read `source` need no change.

## sola-app: handler signature alignment

The browser's current handlers use the pre-`Delivery` shape:

```rust
fn on_menu_action(&mut self, topic: &Topic, ctx: &mut AppCtx)   // OLD
```

Migration is mechanical, mirroring the terminal:

```rust
fn on_menu_action(&mut self, delivery: &Delivery, ctx: &mut AppCtx) {
    let Topic::MenuAction(action) = delivery.topic else { return };
    // …existing body…
}
```

Same change for `on_open_url` and any other registered handlers.

## State schema

### Topics (added to `crates/sola-bus/src/topics.rs`)

```rust
#[persistent(keys = [id], namespace = "browser/tabs/:id")]
BrowserTab(BrowserTab),

#[persistent(namespace = "browser")]
BrowserConfig(BrowserConfig),

#[persistent(namespace = "browser/history")]
BrowserHistory(BrowserHistory),
```

### Payload structs

```rust
pub struct BrowserTab {
    pub id: String,
    pub url: String,
    pub title: String,
    pub ordinal: u32,                    // tab strip order; gaps are fine, JS sorts
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub session_state: Option<String>,   // base64 WebKit page-session blob
}

pub struct BrowserConfig {
    pub active_tab_id: Option<String>,
    // headroom: default_search_engine, zoom_default, etc.
}

pub struct BrowserHistory {
    pub entries: Vec<HistoryEntry>,
}

pub struct HistoryEntry {
    pub url: String,
    pub title: String,
    pub visits: u32,
}
```

`session_state` lives **inline** in each tab's file. Per-key namespace means
each tab already has its own dedicated file (`browser/tabs/<id>.toml`); a
sidecar would just be a second file per tab with no benefit.

History stays a singleton aggregate (Rung 1 from the brainstorm). At ~1000
entries this is a small TOML file; the namespace isolation means visiting a
URL only rewrites `browser/history.toml`, not the shared `state.toml`. If a
future `sola-history` service ever materializes, the schema migrates by
adding a new `RecordVisit` ephemeral topic and retiring `BrowserHistory` —
no breaking change to anything else.

### On-disk layout

```
~/.config/sola/
├── state.toml                  # everything that doesn't opt out
├── browser.toml                # BrowserConfig
└── browser/
    ├── tabs/
    │   ├── <id-1>.toml         # one BrowserTab per file (incl. session_state)
    │   └── <id-2>.toml
    └── history.toml            # BrowserHistory
```

## Browser-side behavior

### `realize_active` — order-independent merge

The bus replays sticky/persistent messages on subscribe in unspecified order.
Both `BrowserConfig` and `BrowserTab` handlers funnel into one idempotent
selection function:

```rust
struct BrowserApp {
    tabs: HashMap<String, BrowserTab>,        // by id
    config: BrowserConfig,
    realized_active_tab_id: Option<String>,   // currently shown WebView
    history: BrowserHistory,
    // …
}

fn on_browser_tab(&mut self, delivery: &Delivery, ctx: &mut AppCtx) {
    let Topic::BrowserTab(tab) = delivery.topic else { return };
    if delivery.retracted {
        self.tabs.remove(&tab.id);
        self.destroy_webview(&tab.id, ctx);
    } else {
        self.upsert_webview(tab, ctx);
        self.tabs.insert(tab.id.clone(), tab.clone());
    }
    self.realize_active(ctx);
}

fn on_browser_config(&mut self, delivery: &Delivery, ctx: &mut AppCtx) {
    let Topic::BrowserConfig(cfg) = delivery.topic else { return };
    self.config = cfg.clone();
    self.realize_active(ctx);
}

/// Selection: config.active_tab_id (if its tab exists) → lowest ordinal → none.
/// No-op when result equals the currently realized selection.
fn realize_active(&mut self, ctx: &mut AppCtx) {
    let target = self.config.active_tab_id.as_deref()
        .filter(|id| self.tabs.contains_key(*id))
        .map(str::to_string)
        .or_else(|| self.tabs.values()
            .min_by_key(|t| t.ordinal)
            .map(|t| t.id.clone()));
    if target != self.realized_active_tab_id {
        self.realized_active_tab_id = target;
        self.show_active_tab(ctx);
    }
}
```

Stale `active_tab_id` referencing a tab that no longer exists falls through
to the lowest-ordinal-tab fallback. No crash, no flicker, no special case.

### Echo filter for `BrowserHistory`

The browser is the canonical owner of the history aggregate. When it emits
`BrowserHistory` after a visit, the bus stores the new sticky and echoes it
to all subscribers — including the browser. Source-filter:

```rust
fn on_browser_history(&mut self, delivery: &Delivery, _ctx: &mut AppCtx) {
    if delivery.source == BrowserApp::APP_ID { return; }   // self-echo
    let Topic::BrowserHistory(h) = delivery.topic else { return };
    self.history = h.clone();
}

fn record_visit(&mut self, url: &str, title: &str, ctx: &mut AppCtx) {
    self.history.record_visit(url, title);
    ctx.emit(Topic::BrowserHistory(self.history.clone()));
}
```

`source = "sola-bus"` (sticky restoration on startup) is **not** filtered —
that's the path that loads existing history into memory. Only `app_id`
matches are skipped, and only one app emits this topic today.

The handler is kept idempotent (`self.history = h.clone()`) so future
external writers (replay tools, debug injection, an eventual `sola-history`
service) just merge cleanly. The source-filter is a clarity/perf
optimization on top of idempotence, not a correctness requirement.

### Persistence triggers

| Event                              | Action                                                            |
|------------------------------------|-------------------------------------------------------------------|
| Tab created                        | emit `BrowserTab(...)` for the new tab                            |
| Tab URL or title changes           | emit `BrowserTab(...)` (whole struct)                             |
| Tab session_state changes (on nav) | emit `BrowserTab(...)`                                            |
| Tab reordered                      | emit `BrowserTab(...)` for each affected tab (new ordinal)        |
| Tab closed                         | retract `BrowserTab(...)`; the bus unlinks `browser/tabs/<id>.toml` |
| Active tab changes                 | emit `BrowserConfig(...)`                                         |
| Visit recorded                     | mutate `self.history`, emit `BrowserHistory(...)` (whole aggregate) |

## Migration of existing on-disk data

One-shot migrator at startup, in `BrowserApp::new`, before bus subscription
takes effect:

1. If `~/.config/sola/browser/` (the new namespace root) does **not** yet
   exist, and any of the legacy files do (`browser-tabs.json`,
   `browser-history.json`):
   - Parse `browser-tabs.json` → for each `PersistedTab`, synthesize an `id`
     (UUIDv4) and `ordinal` (insertion index), build a `BrowserTab`, emit it.
     Emit a `BrowserConfig` with `active_tab_id = None`. The legacy schema
     never persisted a usable tab identity (current restore generates
     throwaway `restored-{i}` ids and unconditionally activates the first
     tab), so there's nothing to map; `realize_active`'s lowest-ordinal
     fallback reproduces the legacy "select first tab" behavior exactly.
   - Parse `browser-history.json` → emit one `BrowserHistory(...)` with
     `entries` copied verbatim.
   - Rename the legacy files to `.migrated` for one cycle, then delete in a
     follow-up cleanup PR.
2. If the new namespace root exists, skip migration entirely (subsequent
   runs).

This preserves session restore for current users without making the bus or
the schema carry legacy structure.

## Test plan

### Unit (sola-bus)

- `path_for` resolution: plain namespace, single-key interpolation, multi-key
  interpolation, no-namespace fallback, non-persistent topic returns `None`.
- Slugification rejection: emitting a keyed topic with a key containing `/`,
  `\0`, `..`, or empty string fails before any disk write.
- `state.rs` writes/reads/retracts route to the resolved path; `state.toml`
  is untouched when only namespaced topics are emitted.
- Loader walks per-key directories and reconstructs key values from path.

### Unit (browser)

- `realize_active` idempotence: calling twice with same state is a no-op.
- `realize_active` ordering: any interleaving of `on_browser_config` and
  `on_browser_tab` events that reaches the same final set yields the same
  selection.
- Stale `active_tab_id` referencing a missing tab falls back to lowest-ordinal.
- Source-filter on `on_browser_history`: emit-then-receive cycle does not
  perturb local state; receive from a different source does.
- Legacy migrator: stub home dir with `browser-tabs.json`/`browser-history.json`,
  run migration, assert emitted topics match expectation; assert files are
  renamed; second run is a no-op.

### Manual smoke

1. `cargo make build` clean.
2. (User runs) `cargo make install browser`. Launch from sola; open three
   tabs; navigate each; switch active to tab 2; close browser.
3. Inspect `~/.config/sola/browser/tabs/` — three `<id>.toml` files; each
   has its url/title/ordinal/session_state. Inspect `~/.config/sola/browser.toml`
   — `active_tab_id` matches tab 2's id.
4. Relaunch sola; reopen browser; verify three tabs, tab 2 active, session
   state restored (back/forward, scroll position).
5. Close one tab; verify its `<id>.toml` is gone.
6. From a previous-version layout (`browser-tabs.json` present, `browser/`
   absent), launch and confirm migrator fires, populates the new layout, and
   renames the legacy file to `.migrated`.

## Implementation sequence (for the plan)

1. Move `apps/browser/` → `crates/sola-browser/`; fix Cargo.toml paths;
   delete stray lockfile. Keep handler bodies untouched but fix signatures
   to use `Delivery`. Verify `cargo make build` clean. (Browser still uses
   `JsonConfig` at this point.)
2. Add `Delivery::source` to sola-bus and propagate in sola-app dispatch.
3. Add `namespace` attribute to `define_topics!` macro; generate `path_for`;
   route writes/reads/retracts; loader walks per-key directories.
4. Add `BrowserTab`, `BrowserConfig`, `BrowserHistory` topics.
5. Replace browser's `JsonConfig` use with bus topics; implement
   `realize_active`, source-filter, persistence triggers.
6. Implement legacy JSON migrator.
7. Update `CLAUDE.md`.

Each step compiles; the browser is functional after step 1 (with old
persistence) and after step 6 (with new persistence). Steps 2–4 affect
sola-bus only and have their own test coverage.
