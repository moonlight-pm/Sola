# sola-debug — runtime introspection for Sola apps

## Goals

Give a developer (human or LLM) a programmatic way to inspect any running
Sola app: list apps and their windows, evaluate JavaScript inside a
WebView and read the result, tail an app's logs, and capture a
screenshot of the compositor output. The CLI is the V1 surface; a GUI
debug app inside the same crate is a planned V2.

The design treats Claude (the LLM) as a first-class consumer. A clean
JSON-in/JSON-out CLI, with predictable exit codes and pipe-friendly
output, is the primary requirement.

## Non-goals (V1)

- GUI debug app. (Planned V2 inside the same crate.)
- Bus inspection commands (`bus tail`, `bus get <topic>`). `sola-monitor`
  already covers most of this; revisit if gaps emerge.
- Forwarding `console.log`/`console.error` through the bus as
  structured events. V1 tails the existing per-app log file at
  `/opt/sola/log/<app>.log`. Move to bus-forwarded console events
  if file-tailing turns out to be lossy or noisy.
- Live REPL / interactive shell mode. One-shot commands for V1.
- Screenshotting individual windows or arbitrary regions. V1 captures
  the whole compositor output; the user can crop the result, or use
  `eval` to query a window's `getBoundingClientRect()` and pass that to
  a future region-aware screenshot.
- Inspecting non-Sola apps (XWayland clients). They have no JS bridge.

## Components

| Component | Role |
|---|---|
| `crates/sola-debug` (new binary) | CLI: subcommands, bus client, request/response correlation, output formatting. |
| `sola-bus/topics.rs` | New topics: `DebugRequest`, `DebugResponse`, `ScreenshotRequest`, `ScreenshotResponse`. |
| `sola-app/lib.rs` | Framework-level handler for `DebugRequest::Eval`. Auto-applies to every Sola app — zero per-app code. |
| `sola-river/client` | Owner of `ScreenshotRequest`. Uses `wlr-screencopy-unstable-v1` (already a Wayland client; the natural home for screencopy work). |

### Why `sola-river` owns screenshot, not `sola-shell`

The user's preference was for the shell to own screenshot. River was
chosen instead because:

1. River is already a `wayland-client` consumer using `wayland-scanner`
   for protocol bindings, and several wlroots-style protocols are
   already vendored there.
2. The shell is GTK4/WebKit6. Driving `wlr-screencopy` from inside a
   GTK process means reaching down into the GDK Wayland backend for the
   `wl_display`, then registering a parallel client on the same
   connection. That works but introduces fragility for no benefit.
3. The bus topic is not coupled to the responder. If we later want a
   richer screenshot UI surface (region picker, hotkey, annotation
   overlay) in the shell, the shell can take ownership of the topic
   without changing the CLI.

## Bus protocol

Two new request/response pairs. Correlation via a `request_id: u64`
generated by the CLI. The responder echoes the same id; the CLI
filters incoming responses by id and ignores unrelated messages.

```rust
// Debug — answered by every Sola app via the framework.
pub struct DebugRequestPayload {
    pub request_id: u64,
    pub target_app: String,        // app_id; only the matching app responds
    pub op: DebugOp,
}
pub enum DebugOp {
    Eval { window: Option<String>, expr: String },
    ListWindows,
}

pub struct DebugResponsePayload {
    pub request_id: u64,
    pub source_app: String,
    pub result: DebugResult,
}
pub enum DebugResult {
    Json(serde_json::Value),
    Error(String),
}

// Screenshot — answered by sola-river.
pub struct ScreenshotRequestPayload {
    pub request_id: u64,
    pub path: Option<PathBuf>,     // None → auto-generate under /tmp/sola/screenshots/
}
pub struct ScreenshotResponsePayload {
    pub request_id: u64,
    pub result: Result<PathBuf, String>,
}
```

`Topic::DebugRequest`, `Topic::DebugResponse`,
`Topic::ScreenshotRequest`, and `Topic::ScreenshotResponse` are all
ephemeral (not sticky — request/response semantics, no replay).

A `request_id` collision across concurrent CLI invocations is harmless:
each invocation generates its id from `rand::random` and filters
responses by that id, so cross-talk is impossible in practice.

## CLI surface

```
sola-debug apps
sola-debug eval <app> [--window <title>] [--timeout <secs>] "<expression>"
sola-debug logs [<app>] [-f|--follow]
sola-debug screenshot [-o <path>]
```

### Behaviour

- `apps` reads the sticky `Topic::Windows` snapshot, groups by `app_id`,
  prints a JSON object: `{ "<app_id>": [{"title": "...", "window_id": N}, ...] }`.
- `eval` defaults to a 5-second timeout. The expression is wrapped (see
  Eval flow below) so async results, exceptions, and non-JSON-serializable
  values all reduce to a JSON value or an error string. On success,
  prints the JSON result and exits 0. On error, prints
  `{"error": "..."}` to stdout and exits 1. On timeout, exits 2.
- `logs` tails `/opt/sola/log/<app>.log` via the standard
  `std::io::BufRead` loop; `-f` keeps the tail open.
- `screenshot` writes a PNG to `<path>` (or
  `/tmp/sola/screenshots/<unix-ts>.png` if `-o` not given) and prints
  the path on success.

## Eval flow

```
                    +------------------+
                    |   sola-debug     |
                    |   (CLI client)   |
                    +--------+---------+
                             |
                             |  DebugRequest { request_id, target_app, op }
                             v
                       +-----+------+
                       |  sola-bus  |
                       +-----+------+
                             |
                             v
                  +----------+-----------+
                  |  sola-app framework  |   (in target_app's process)
                  |   intercepts request |
                  +----------+-----------+
                             |
              wraps expr in try/JSON.stringify, eval_js into target window
                             |
                             v
                   +---------+---------+
                   |  WebView (JS)     |
                   +---------+---------+
                             |
              calls window.__solaCmd('__debug_result__', { request_id, value/error })
                             |
                             v
                  +----------+-----------+
                  |  sola-app framework  |
                  |  intercepts cmd      |
                  |  emits DebugResponse |
                  +----------+-----------+
                             |
                             v
                       +-----+------+
                       |  sola-bus  |
                       +-----+------+
                             |
                             v
                       +-----+------+
                       |  sola-debug |
                       |  prints JSON |
                       +-------------+
```

Wrapper script the framework injects (concrete form):

```js
(async () => {
  try {
    const value = await (async () => { return (USER_EXPR); })();
    window.__solaCmd('__debug_result__', { request_id: <id>, value });
  } catch (e) {
    window.__solaCmd('__debug_result__', { request_id: <id>, error: String(e) });
  }
})()
```

The framework intercepts the `__debug_result__` command in the JS
dispatcher *before* user code sees it (similar to how `Copy`/`Paste`
are intercepted before the user app's bus registry). The intercepted
result is converted to a `DebugResponse` and emitted on the bus.

### Window resolution

`window: Option<String>` matches against `WindowHandle::title()`.
`None` selects the first window in `ctx.windows`. Unknown title
returns `DebugResult::Error("no window matching title 'X'")`.

### Why use the JS bridge instead of WebKit's `evaluate_javascript` callback

`evaluate_javascript` returns a `JSCValue` via async callback. Converting
that to `serde_json::Value` is non-trivial (no public WebKit API to
flatten arbitrary JSCValue → JSON), and the callback API is awkward to
plumb through the bus (we'd need to keep the `Cancellable` and the
in-flight CLI request alive across an arbitrary delay).

The JS bridge already exists, already handles JSON, and already lives
on the GTK main loop. Reusing it is strictly simpler.

## Screenshot flow

`sola-river` binds `zwlr_screencopy_manager_v1` at startup alongside the
existing wayland globals. On `ScreenshotRequest`:

1. Pick the first `wl_output` (V1 is single-output).
2. Create a screencopy frame; on `Buffer` event, allocate a `wl_shm`
   buffer of the announced size and format.
3. Call `frame.copy(buffer)`.
4. On `Ready`, mmap the SHM region, convert pixels to RGB if needed,
   PNG-encode via `image::ImageBuffer::save`.
5. Emit `ScreenshotResponse { request_id, result: Ok(path) }`.
6. On `Failed`, emit `ScreenshotResponse { request_id, result: Err(msg) }`.

The capture is async (multiple Wayland events). We track in-flight
captures in an `AppData` field keyed by `request_id` so multiple
concurrent screenshots don't trample each other.

### Dependencies added to sola-river

- `wayland-protocols-wlr` (or vendor `wlr-screencopy-unstable-v1.xml` and
  generate via `wayland-scanner`, matching the existing pattern).
- `image` (PNG encoding).
- `memmap2` or `rustix::mm` for mmap on the SHM fd.

## CLI implementation notes

- The CLI is a one-shot bus client: connect, identify, emit the request,
  block on `recv_timeout` for the matching response, print, exit.
- The CLI subscribes to `DebugResponse` (or `ScreenshotResponse`) before
  emitting, so it doesn't race against the responder.
- For `apps`, no request is sent; the CLI just subscribes to `Windows`
  and waits for the sticky replay.
- Exit codes: 0 = success, 1 = remote error, 2 = timeout, 3 = local
  error (bus connect failed, target app not running, etc.).

## Risks / open questions

- **`JSON.stringify(domNode)` returns `{}`.** Documented in the CLI
  help: callers should project to `{tag, id, classes, rect, computed}`
  themselves. A future `--smart` mode could install a JSON replacer
  that flattens `Element`/`NodeList` automatically.
- **CLI cold-start cost.** Each invocation reconnects to the bus and
  receives the full sticky replay. For a tight loop of `eval` calls
  this is wasteful. V2 may add a `--keep-alive` mode that batches.
- **Screenshot multi-output.** V1 captures the first output. Multi-
  monitor users will need to pick by name once we support it.
- **Result envelope.** `DebugResult::Json(Value)` plus a separate
  `Error` variant lets the CLI distinguish remote success from remote
  failure cleanly. An alternative `Result<Value, String>` would
  serialize as a tagged enum that's slightly less natural over the
  wire — keeping the explicit enum form.
