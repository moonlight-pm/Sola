> each, same URL (`https://slate.auto`), same iced chrome, same
> hardware (NVIDIA proprietary, RTX 3090 Ti). Generated by

## Interpretation

| dimension          | winner | margin                                  |
| ------------------ | ------ | --------------------------------------- |
| CPU steady-state   | CEF    | ~2× lower (30% vs 65% tree CPU)         |
| Memory             | WPE    | ~25% lower (1.23 GB vs 1.65 GB)         |
| GPU util / memory  | tie    | within noise (whole-GPU, not per-proc)  |
| Frame re-emission  | n/a    | see below                               |

### CPU asymmetry

WPE's pipeline re-emits frames on every render tick even when
nothing on the page is changing — see "shader FPS" in WPE's row:
a steady ~100 fps even though `slate.auto` after first paint is
mostly static. CEF's compositor batches paints to *actual*
visual changes, so the shader sees ~0–1 fps in steady state and
the corresponding GPU/CPU work doesn't happen. That's a real
CEF win, but it's a *pipeline-policy* win as much as a
raw-perf one — once we land scroll / animation, CEF's paint
count will rise to match what WPE is already doing.

### Memory asymmetry

CEF runs more helper processes (9 vs 8), each with its own
sandbox and Skia/V8 working set, which adds up to roughly
400 MiB. WebKit's WPE port is more monolithic. Scale to N
browser windows and the gap likely widens because each CEF
window spawns more helpers.

### Visual quality (qualitative, not in the table)

WebKit-rendered text on this hardware looks slightly softer
than Chromium-rendered text. Same Skia backend, different glyph
hinting / subpixel positioning / CSS-pixel snapping. Not a
defect, but worth noting before declaring a winner on perceived
quality.

### Caveats baked in

- CEF is on the **CPU OSR** path (`on_paint` + `queue.write_texture`)
  because NVIDIA proprietary can't drive CEF's dma-buf OSR — see
  the project plan for the long version. On a Mesa stack (Intel
  / AMD / NVK), CEF's CPU% should drop further because the GPU
  process can render directly into a dma-buf instead of reading
  back to a CPU buffer.
- WPE is on the **GPU dma-buf** path (zero-copy import via
  modifier-aware Vulkan), which is the best transport it has
  on NVIDIA.
- "CPU%" is `ps -o %cpu` summed across the process tree —
  *averaged since process start*. Interval CPU would give
  sharper numbers; this is enough to call a 2× delta but not
  to call a 5% delta.

## Reproduce

```sh
cargo make build sola-browser-wpe
cargo make build sola-browser-cef

bench/run-bench.sh wpe https://slate.auto 30 docs/notes/data/wpe-slate
bench/run-bench.sh cef https://slate.auto 30 docs/notes/data/cef-slate
bench/summarize.py docs/notes/data/wpe-slate docs/notes/data/cef-slate \
    -o docs/notes/2026-05-21-wpe-vs-cef-bench.md
```

  FPS numbers to mean more.
